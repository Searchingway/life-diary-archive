# 人生档案 Diary — 技术选型

> 当前主版本：`diary_v2.0/`（4.0 桌面端，全部界面和技术栈重构）
> 
> 旧版 `src/life_dairy/`（纯 PySide6 组件版）仍作为后端数据层被新版兼容引用。

## 整体架构

```
React 前端 (diary_v2.0/Untitled/)
       │  HTTP REST API
       ▼
Python HTTP 服务器 (diary_v2.0/launcher.py - LifeDiaryHandler)
       │  导入旧版 storage / export 模块
       ▼
JSON 文件系统 (data/Diary/)
       │
PySide6 + QWebEngineView (桌面壳，包裹 Web 界面)
```

## 整体设计原则

| 原则 | 体现 |
|------|------|
| **本地优先** | 所有数据存本地文件，无网络请求 / 云同步 / 账号系统 |
| **文件即数据库** | 不用 SQLite / NoSQL，目录树 + JSON 做查询和关联 |
| **前后端分离** | Python HTTP API + React SPA，通过 REST 通信 |
| **渐进式架构** | 4.0 保留了 `src/life_dairy/` 的 Storage/Export 层，前端从 PySide6 组件迁移到 Web |
| **预览-确认** | AI 功能统一使用预览弹窗，不自动写入数据 |

## 选型逻辑

- **为什么从 PySide6 组件迁到 Web？** 4.0 重构的本质是将 UI 从 Qt Widgets 迁移到 React + MUI，获得更现代的 UI 组件生态和开发效率。后端数据层保持不变，降低迁移风险。
- **为什么保留 PySide6 壳？** 保持桌面原生体验（系统托盘、文件对话框、窗口管理），同时享受 Web 前端的灵活性。
- **为什么用 Python http.server 而不是 FastAPI？** 个人本地工具，单用户场景，标准库零依赖启动。
- **为什么不用 SQLite？** 文件系统存储让备份 / 恢复 / ZIP 互通直接操作目录树，用户可以直接用文件管理器浏览数据，符合"不锁定数据"的设计目标。
- **为什么深依赖 `src/life_dairy/`？** `launcher.py` 直接 import 旧版的 Storage / Export / Models，避免后端重写，是务实的迁移策略。

## 项目结构

```
diary_v2.0/                 # 当前主版本
  ├── Untitled/               # React + TypeScript 前端
  │   ├── src/app/            # 前端源码
  │   │   ├── pages/          # 页面组件（15 个模块页面）
  │   │   ├── components/     # 通用组件
  │   │   └── lib/            # API 客户端
  │   └── dist/               # 构建产物
  ├── launcher.py             # Python HTTP 服务 + PySide6 桌面壳（~1600 行）
  └── data/Diary/             # 运行时数据目录
src/life_dairy/              # 旧版桌面端源码（仍被 launcher.py 引用为数据层）
  ├── 13 个 Storage 类
  ├── 14 个 Page 类（部分不再渲染）
  ├── Models、Exporters、BackupService 等
  └── ai_service.py / ai_dialogs.py
data/Diary/                  # 用户数据根目录（两版共用）
```
